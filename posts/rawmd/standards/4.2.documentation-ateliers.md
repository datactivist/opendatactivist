## 4.2 - Documenter les temps de travail et les décisions

La documentation des débats et des décisions permet de s'assurer que chacun·e puisse suivre, voire rattraper en cours de route, l'évolution du processus de co-conception. 

![1-1](/images/algo/1-1.png)

### Créer un espace de partage des supports

L'espace de documentation doit être public et accessible sans inscription préalable, pour permettre à tout acteur intéressé de consulter l'avancée des travaux. Il doit centraliser l'ensemble des supports (comptes-rendus, présentations, ressources, versions successives du standard) pour éviter la dispersion de l'information.

GitHub répond à la plupart de ces critères : il offre un historique complet des modifications, permet la collaboration à plusieurs, et autorise la création de mini-sites web via GitHub Pages. Son interface peut cependant rebuter des contributeurs non familiers du développement logiciel. Une approche possible consiste à coupler GitHub (pour la traçabilité et la publication finale) avec un outil plus accessible pour la collaboration au quotidien (Google Docs, Framapad, Notion), en prévoyant une synchronisation régulière entre les deux.

### Faire des comptes-rendus de tous les échanges

La documentation des échanges doit être systématique et fidèle à la richesse des débats. L'approche "Chatham House Rule" est recommandée : les idées et arguments sont rapportés fidèlement, mais sans attribution nominative. Cette règle libère la parole en permettant aux participants d'exprimer des positions nuancées sans crainte d'être définitivement étiquetés sur une position.

Il est important de ne pas édulcorer les débats ou de gommer les points de tension. Les désaccords et les objections doivent être documentés avec la même précision que les consensus — ils permettent aux futurs contributeurs de comprendre les enjeux réels et d'éviter de rouvrir des débats déjà tranchés. Une innovation utile consiste à inverser le processus habituel en faisant passer les participants par l'écrit avant l'oral : contributions sur Miro ou tableau blanc physique, puis développement oral. Cette approche assure une traçabilité immédiate et améliore la qualité des échanges.

### Communiquer largement après chaque atelier, en annonçant la prochaine étape

La communication post-atelier doit être systématique et multi-canal. Elle ne doit pas se limiter aux participants effectifs, mais viser l'ensemble de la communauté potentiellement intéressée. L'objectif est d'éviter les boucles fermées où seuls les "initiés" sont informés des avancées.

Le contenu de cette communication doit équilibrer un résumé accessible des principales décisions prises, les points encore en débat qui nécessitent des contributions supplémentaires, les prochaines échéances avec leurs modalités de participation, et un renvoi vers l'espace de documentation. La récurrence de cette communication est ce qui maintient la dynamique sur un processus qui s'étale nécessairement sur plusieurs mois.

### Exemple : l'usage de GitHub pour documenter les avancées du standard

GitHub offre un cadre particulièrement abouti pour la documentation d'un standard, d'autant plus utile que le schéma lui-même y sera hébergé — ce qui centralise tout en un seul endroit. Le fichier README constitue la porte d'entrée du projet (objectif, état d'avancement, modalités de contribution). Le système d'issues permet de tracer finement les débats : chaque point de discussion peut faire l'objet d'une issue dédiée, avec possibilité pour tous les contributeurs de commenter et de suivre l'évolution.

Le système de versions (tags et releases) formalise les étapes du processus : version de consultation, version 1.0, versions correctives ultérieures. GitHub Pages génère automatiquement un site de présentation accessible au grand public, synchronisé avec l'évolution du projet. Cette approche assure une pérennité maximale : même en cas de changement d'équipe projet, l'historique complet reste accessible.
