## 4.2 - Documenter les temps de travail et les décisions

La documentation des débats et des décisions permet de s'assurer que chacun·e puisse suivre, voire rattraper en cours de route, l'évolution du processus de co-conception.

![1-1](/images/algo/1-1.png)

### Créer un espace de partage des supports

L'espace de documentation doit être public et accessible sans inscription préalable — le but est que quelqu'un qui découvre la démarche en cours de route puisse retrouver l'historique complet et comprendre les choix effectués.

GitHub répond à la plupart de ces critères : historique des modifications, collaboration à plusieurs, possibilité de créer un mini-site via GitHub Pages. C'est un outil très transparent, mais franchement très "geek" — son interface peut rebuter des contributeurs non développeurs. Une option consiste à coupler GitHub avec un outil plus accessible pour la collaboration au quotidien (Google Docs, Framapad, Notion).

### Faire des comptes-rendus de tous les échanges

Nous recommandons l'approche "Chatham House" : les idées et arguments sont rapportés fidèlement, mais sans attribution nominative. Cette règle libère un peu la parole — les gens peuvent s'exprimer sans craindre qu'une position provisoire soit gravée dans le marbre.

À éviter : édulcorer les débats ou gommer les tensions. Les désaccords et les points de blocage méritent d'être retracés avec autant de soin que les consensus.

Une piste utile que nous préconisons : partir de l'écrit pour aller vers l'oral, plutôt que l'inverse. Sur un tableau blanc en ligne (Miro) ou physique, chacun pose ses idées par écrit avant de les développer à l'oral. Ça force à réfléchir avant de parler.

### Communiquer largement après chaque atelier, en annonçant la prochaine étape

Un risque classique dans les démarches de standardisation : des acteurs qui découvrent le résultat final et disent "on n'était pas au courant, c'est fait dans votre coin". S'il y a des listes de diffusion au sein de la communauté métier, c'est là qu'il faut faire paraître les comptes-rendus et renvoyer vers la documentation — pas rester dans une boucle mail de quinze personnes.

Même si la grande majorité des destinataires ne participera pas, l'important est qu'ils aient eu la possibilité de le faire.

### Exemple : l'usage de GitHub pour documenter les avancées du standard

GitHub a l'avantage de centraliser en un seul endroit le schéma technique et toute la documentation de sa conception — l'historique, les débats, les décisions. C'est d'autant plus pertinent que le schéma de données lui-même sera hébergé sur GitHub. Le fichier README constitue la porte d'entrée du projet. Le système d'issues permet de tracer les débats : chaque point fait l'objet d'une issue, ouverte à tous les contributeurs. GitHub Pages génère automatiquement un site lisible par le grand public.
