## 4.2 - Documenter les temps de travail et les décisions

La documentation des débats et des décisions permet de s'assurer que chacun·e puisse suivre, voire rattraper en cours de route, l'évolution du processus de co-conception.

### Créer un espace de partage des supports

L'espace de documentation doit être public et accessible sans inscription préalable — le but est que quelqu'un qui découvre la démarche en cours de route puisse retrouver l'historique complet et comprendre les choix effectués.

GitHub ou GitLab répondend à la plupart de ces critères : historique des modifications, collaboration à plusieurs, possibilité de créer un mini-site. C'est un outil très transparent mais avec un coût à l'entrée pour les personnes les moins techniques : son interface peut rebuter des contributeurs. Une option consiste à coupler GitHub/GitLab avec un outil plus accessible pour la collaboration au quotidien (Framapad, La Suite, Notion, Google Docs).

### Faire des comptes-rendus de tous les échanges

Nous recommandons l'approche "Chatham House" : les idées et arguments sont rapportés fidèlement, mais sans attribution nominative. Les personnes peuvent ainsi s'exprimer sans craindre qu'une position provisoire soit gravée dans le marbre.

À éviter : édulcorer les débats ou gommer les tensions. Les désaccords et les points de blocage méritent d'être retracés avec autant de soin que les consensus.

Une piste utile que nous préconisons : partir de l'écrit pour aller vers l'oral, plutôt que l'inverse. Sur un tableau blanc en ligne (Miro) ou physique, chacun pose ses idées par écrit avant de les développer à l'oral. Cela force à réfléchir avant de parler.

### Communiquer largement après chaque atelier, en annonçant la prochaine étape

Un risque classique dans les démarches de standardisation : des acteurs peuvent découvrir le résultat final et regretter ne pas avoir été tenus au courant. Les comptes-rendus et la documentation peuvent être envoyés sur des listes de diffusion au sein de la communauté métier. 

Même si la grande majorité des destinataires ne participera pas, l'important est de leur laisser la possibilité de le faire.

### Exemple : l'usage de GitHub ou GitLab pour documenter les avancées du standard

GitHub ou GitLab ont l'avantage de centraliser en un seul endroit le schéma technique et toute la documentation de sa conception — l'historique, les débats, les décisions. C'est d'autant plus pertinent que le schéma de données lui-même sera hébergé sur l'un des deux. 
Le fichier README constitue la porte d'entrée du projet. 
Le système de comit permet de retracer l'ensemble des modifications (nécessaire pour la transparence de la démarche). 
Les issues permettent de tracer les débats : chaque point fait l'objet d'une issue, ouverte à tous les contributeurs. 
GitHub Pages génère automatiquement un site lisible par le grand public.
